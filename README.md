# Лабораторная работа № 1: защищённый REST API на Spring Boot

Это учебное приложение на **Java 17, Spring Boot 4.1.1 и Maven**. Пользователь регистрируется, входит по логину и паролю, получает JWT и с этим токеном создаёт и читает **свои** записи. Проект показывает защиту от SQL-инъекций, XSS и ошибок аутентификации, а также автоматические проверки кода и зависимостей в GitHub Actions.

Данные хранятся во встроенной H2 **в памяти**: после остановки приложения пользователи и записи исчезают. Это удобно для лабораторной работы; при каждом новом запуске сценарий начинается с регистрации.

## Что должно быть установлено

- JDK 17. Проверьте: java -version.
- Git. Проверьте: git --version.
- curl и Python 3 для команд из примера. Можно использовать Postman и вручную копировать токен.
- Доступ в интернет при первой сборке Maven и при обновлении базы уязвимостей OWASP Dependency-Check.

Maven отдельно устанавливать не требуется: файл **mvnw** запускает Maven Wrapper и при необходимости скачивает нужную версию Maven.

## Устройство проекта

Стандартное расположение Maven помогает IDE, Maven и CI одинаково находить исходники, настройки и тесты:

~~~text
.

├── mvnw / mvnw.cmd                 Maven Wrapper для macOS/Linux и Windows
├── .mvn/wrapper/                   настройки Wrapper
├── .github/workflows/ci.yml       GitHub Actions: тесты, SAST, SCA
├── src/
│   ├── main/
│   │   ├── java/org/hipeoplea/secureapi/
│   │   │   ├── SecureApiApplication.java
│   │   │   ├── auth/               регистрация, вход, выдача JWT
│   │   │   │   └── dto/           входные и выходные модели auth API
│   │   │   ├── user/              пользователь и доступ к таблице пользователей
│   │   │   ├── post/              защищённые записи и их обработка
│   │   │   │   └── dto/           входные и выходные модели записей
│   │   │   ├── config/            Spring Security и проверка JWT
│   │   │   └── common/            единая обработка ошибок

│   └── test/java/                 проверка поведения API
~~~

Что делает каждый слой:

| Путь | Назначение |
| --- | --- |
| **SecureApiApplication.java** | Точка входа. Запускает Spring Boot и создание компонентов приложения. |
| **auth/AuthController.java** | Принимает HTTP-запросы регистрации и входа, вызывает сервис, задаёт HTTP-ответ. |
| **auth/AuthService.java** | Проверяет учётные данные и правила регистрации, хэширует пароли, создаёт токен. |
| **auth/JwtService.java** | Подписывает JWT после успешного входа. |
| **auth/dto/** | Отдельные Java-классы для JSON-запросов и ответов. Например, RegisterRequest и TokenResponse. Эти классы не являются таблицами БД. |
| **user/User.java, UserRepository.java** | JPA-сущность пользователя и доступ к ней через Spring Data JPA. |
| **post/Post.java, PostRepository.java** | JPA-сущность записи и запросы к таблице записей. |
| **post/DataController.java, DataService.java** | Защищённые HTTP-методы и бизнес-логика: запись сохраняется за текущим пользователем, а список отбирается по владельцу. |
| **post/dto/** | CreatePostRequest и PostResponse: формат JSON отделён от сущностей БД; хэш пароля и служебные поля не попадают в ответ. |
| **config/SecurityConfig.java** | Указывает, какие URL открыты, какие требуют входа; включает проверку Bearer JWT через Spring Security. |
| **config/JwtConfig.java** | Настраивает ключ, подпись и проверку JWT. |
| **common/ApiExceptionHandler.java** | Превращает типовые ошибки в понятные HTTP-ответы без stack trace и внутренних деталей. |
| **application.properties** | Адрес H2, параметры JPA и JWT; сам секрет здесь не хранится. |
| **pom.xml** | Описывает зависимости и задачи Maven, включая SpotBugs и OWASP Dependency-Check. |

Поток одного защищённого запроса:

~~~text
curl/Postman
   → Spring Security проверяет подпись и срок JWT
   → DataController получает подтверждённого пользователя
   → DataService выполняет операцию только для этого пользователя
   → PostRepository обращается к H2 через JPA
   → PostResponse возвращается как JSON
~~~

Контроллер не собирает SQL и не проверяет подпись JWT самостоятельно: за каждую задачу отвечает свой слой или библиотека Spring.

## Как запустить локально

В терминале перейдите в корень проекта, где находится **pom.xml**. Для JWT нужен случайный ключ длиной не менее 32 байт. Команда ниже создаёт 32 случайных байта и кодирует их в Base64; ключ живёт только в текущем сеансе терминала.

**macOS/Linux:**

~~~bash
export JWT_SECRET_BASE64="$(openssl rand -base64 32)"
./mvnw spring-boot:run
~~~

**Windows PowerShell:**

~~~powershell
$bytes = New-Object byte[] 32
$rng = [System.Security.Cryptography.RandomNumberGenerator]::Create()
$rng.GetBytes($bytes)
$rng.Dispose()
$env:JWT_SECRET_BASE64 = [Convert]::ToBase64String($bytes)
.\mvnw.cmd spring-boot:run
~~~

Дождитесь строки о запуске приложения. API доступен по адресу **http://localhost:8080**. Если порт 8080 занят, остановите другую программу на нём или настройте server.port в application.properties.

Секрет нельзя помещать в Git. После открытия нового терминала переменную нужно задать снова. При смене секрета ранее выданные токены перестают проходить проверку подписи.

### Запуск в IntelliJ IDEA

1. Откройте **папку проекта**, содержащую pom.xml. IDE должна определить Maven-проект и загрузить зависимости.
2. Проверьте **Project SDK = JDK 17**.
3. Откройте конфигурацию запуска SecureApiApplication и добавьте переменную окружения **JWT_SECRET_BASE64**. Значение можно получить командой openssl rand -base64 32 в терминале.
4. Запустите SecureApiApplication. Для запросов используйте терминал, Postman или встроенный HTTP-клиент IDE.

Если IntelliJ IDEA всё ещё показывает старую конфигурацию Gradle этого каталога, откройте **pom.xml** как Maven-проект и обновите зависимости в окне Maven. Для сборки в терминале настройки IDE не нужны.

## API: повторите сценарий по шагам

Там, где у запроса или ответа есть тело, используется JSON; успешная регистрация возвращает статус 201 без тела. Методы **/auth/register** и **/auth/login** открыты. Для **/api/data** нужен заголовок **Authorization: Bearer JWT_ИЗ_ОТВЕТА**. Токен действует 15 минут.

| Метод | Адрес | Доступ | Результат |
| --- | --- | --- | --- |
| POST | /auth/register | Без токена | Создать пользователя; 201 Created |
| POST | /auth/login | Без токена | Получить JWT; 200 OK |
| GET | /api/data | Bearer JWT | Список своих записей; 200 OK |
| POST | /api/data | Bearer JWT | Создать свою запись; 201 Created |

Примеры ниже выполняются в **macOS/Linux**. В PowerShell удобно выполнять запросы в Postman: ответ входа содержит токен, который можно вставить в заголовок Authorization.

### 1. Создать пользователя — POST /auth/register

~~~bash
curl -i -X POST http://localhost:8080/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"username":"student1","password":"long-unique-password-1"}'
~~~

Ожидается **201 Created**. Повторная регистрация того же логина возвращает **409 Conflict**. Логин содержит 3–32 символа: латинские буквы, цифры, точку, дефис или подчёркивание. Пароль должен содержать 12–72 символа и не превышать 72 байта в UTF-8: это ограничение BCrypt. Пустые или неверные поля дают **400 Bad Request**.

### 2. Войти — POST /auth/login

~~~bash
curl -i -X POST http://localhost:8080/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"student1","password":"long-unique-password-1"}'
~~~

При успехе сервер возвращает **200 OK** и JSON с полями **accessToken**, **tokenType**, **expiresInSeconds**. Неверная пара логин/пароль даёт **401 Unauthorized** с одинаковой формулировкой независимо от того, существует ли пользователь.

Форма успешного ответа (сам токен здесь сокращён):

~~~json
{"accessToken":"eyJ...","tokenType":"Bearer","expiresInSeconds":900}
~~~

Чтобы сохранить токен в переменную текущего терминала:

~~~bash
TOKEN="$(curl -sS -X POST http://localhost:8080/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"student1","password":"long-unique-password-1"}' \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["accessToken"])')"
~~~

Проверить, что переменная непустая, можно командой **test -n "$TOKEN" && echo "Токен получен"**. Не публикуйте значение токена в README или скриншотах: до истечения срока это доступ к API от вашего имени.

### 3. Проверить запрет без токена — GET /api/data

~~~bash
curl -i http://localhost:8080/api/data
~~~

Ожидается **401 Unauthorized**. Так видно, что одного знания адреса метода недостаточно.

### 4. Создать запись — POST /api/data

~~~bash
curl -i -X POST http://localhost:8080/api/data \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"title":"Моя запись","content":"Текст для лабораторной"}'
~~~

Ожидается **201 Created** и JSON созданной записи. Заголовок title обязателен и содержит до 200 символов, текст content — до 2000 символов. В запросе нет поля владельца: сервер берёт его из проверенного токена. Клиент не может назначить владельцем другого пользователя.

### 5. Получить свои записи — GET /api/data

~~~bash
curl -i http://localhost:8080/api/data \
  -H "Authorization: Bearer $TOKEN"
~~~

Ожидается **200 OK** и JSON-массив из не более 100 последних записей текущего пользователя. Чтобы проверить разграничение доступа, создайте второго пользователя, войдите под ним и повторите GET: записи первого пользователя не должны отображаться.

### 6. Показать экранирование пользовательского текста

~~~bash
curl -i -X POST http://localhost:8080/api/data \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"title":"<script>alert(1)</script>","content":"<b>текст</b>"}'
~~~

В JSON-ответе символы HTML в пользовательских полях должны быть представлены, например, как **&lt;script&gt;** и **&lt;b&gt;**. В Postman посмотрите вкладку **Raw**: её представление ближе к фактическому HTTP-ответу.

## Как устроена защита

### SQL-инъекции

**Spring Data JPA** формирует запросы к H2 и передаёт значения параметрами. Например, UserRepository.findByUsername(username) ищет пользователя, а PostRepository.findTop100ByOwnerOrderByIdDesc(owner) выбирает записи по владельцу. Логин, текст и владелец не вставляются строковой конкатенацией в SQL. Поэтому строка пользователя не может превратиться в новый фрагмент SQL-команды. Валидация ввода дополняет эту защиту, но не заменяет параметризацию.

### XSS

Приложение возвращает JSON, а пользовательские строковые поля при формировании PostResponse в DataService проходят **HtmlUtils.htmlEscape**. Например, введённое **<script>** возвращается как **&lt;script&gt;**. Контроллер также не отдаёт произвольный HTML-шаблон из пользовательского ввода. При создании отдельного веб-интерфейса его разработчик всё равно должен безопасно выводить данные в зависимости от контекста HTML/JavaScript; защита JSON API не заменяет защиту интерфейса.

### Пароли и JWT

- Пароль сохраняется в базе только в виде **BCrypt-хэша** с фактором стоимости 12. PasswordEncoder создаётся в SecurityConfig, а AuthService применяет его при регистрации и входе. Случайная соль входит в результат BCrypt; исходный пароль нельзя получить из хэша.
- При входе пароль сверяется с хэшем через PasswordEncoder. API не возвращает пароль или хэш.
- После успешной проверки JwtService выдаёт подписанный **JWT HS256** на 15 минут. Токен состоит из заголовка, полезной нагрузки и подписи. В нём указан пользователь; секрет для подписи приходит из **JWT_SECRET_BASE64**.
- Spring Security OAuth2 Resource Server проверяет Bearer-токен: подпись, срок действия и issuer. Запрос с отсутствующим, неверным или просроченным токеном отклоняется.
- Для чтения и записи данных сервер использует личность из проверенного токена. Переданный клиентом идентификатор другого пользователя не используется.

JWT — это подписанный токен, а не шифрование: его содержимое можно прочитать. В него нельзя класть пароль, секреты и персональные данные без необходимости. Для реальной публикации API нужен HTTPS, секрет в защищённом хранилище, постоянная база и ограничение частоты попыток входа.

### Валидация и ошибки

Bean Validation проверяет поля запросов до сохранения в БД. Обработчик ошибок возвращает соответствующие HTTP-статусы, не раскрывая SQL, stack trace или пароль. Ограничение длины поля помогает избежать чрезмерного расхода ресурсов.

## Локальные проверки

Быстрая проверка после изменения кода:

~~~bash

~~~

Интеграционные тесты проверяют отказ без токена и с неверным токеном, регистрацию и BCrypt-хэш, получение JWT, создание и чтение записи, экранирование HTML, изоляцию записей разных пользователей и отказ на попытку входа с SQL-подобной строкой. Тест задаёт отдельный учебный JWT-ключ через DynamicPropertySource, поэтому переменная окружения для него не требуется. Итог виден в терминале; подробные результаты находятся в **target/surefire-reports/**.

В этом каталоге команда `./mvnw test` завершилась успешно: 2 теста, 0 ошибок. Отдельный запуск через `./mvnw spring-boot:run` и `curl` дал 401 без токена, 201 при регистрации и создании записи, 200 при чтении с JWT; HTML-теги в ответе были экранированы.

Сканеры вызываются **отдельными Maven goals**, поэтому обычная команда mvnw verify запускает сборку и тесты, но не заменяет команды ниже. Для SCA требуется актуальная база уязвимостей NVD; первая загрузка занимает время и требует сети. Задайте ключ NVD и выполните:

~~~bash
export NVD_API_KEY="<ВАШ_NVD_API_KEY>"
./mvnw -B -ntp -DskipTests package spotbugs:check
./mvnw -B -ntp dependency-check:check
~~~

SpotBugs исследует скомпилированный код (**SAST**), а OWASP Dependency-Check сопоставляет версии библиотек с известными уязвимостями (**SCA**). Goal spotbugs:check сам запускает анализ перед проверкой результата. Локальные отчёты: **target/reports/spotbugs.html** (плюс target/spotbugsXml.xml) и **target/dependency-check-report.html**. Порог CI для уязвимостей зависимостей — **CVSS 7.0**: находка с таким или более высоким баллом приводит к ошибке проверки. Успешный статус означает, что настроенные сканеры завершились без блокирующих находок; он не доказывает отсутствие всех возможных уязвимостей.

## GitHub Actions и отчёты

Файл **.github/workflows/ci.yml** запускает проверки при каждом **push** и **pull request**; возможен и ручной запуск из вкладки Actions. Workflow использует JDK 17 и Maven Wrapper. Отдельные задачи выполняют тесты, SpotBugs и Dependency-Check; отчёты сканеров сохраняются как артефакты запуска. Если проверка упадёт, отчёт может помочь найти причину.

GitHub не передаёт секреты репозитория в запросы на включение изменений из внешних форков. Для таких PR задача SCA остановится с сообщением об отсутствии `NVD_API_KEY`; учебный сценарий с ветками и PR внутри вашего репозитория после настройки секрета работает полностью.

Для успешного запуска задачи SCA нужен ключ NVD: workflow проверяет наличие секрета **NVD_API_KEY** до старта сканера. Сначала создайте репозиторий по инструкции ниже, затем **до первого push**:

1. Запросите личный NVD API key на официальном сайте NVD (раздел **Developers → Request an API Key**).
2. В GitHub откройте свой репозиторий → **Settings → Secrets and variables → Actions**.
3. Нажмите **New repository secret**; имя — **NVD_API_KEY**, значение — полученный ключ.
4. Сохраните секрет. Не добавляйте ключ в Git, pom.xml, README или скриншоты.

Если первый запуск состоялся без секрета, добавьте его и запустите workflow повторно через **Actions → Secure REST API CI → Run workflow**. Первый прогон SCA обычно дольше следующих из-за загрузки базы CVE.

### Как получить скриншоты для сдачи

Скриншоты результатов из GitHub можно сделать только **после публикации и реального запуска** workflow:

1. Откройте вкладку **Actions** и последний успешный запуск **Secure REST API CI**. Скопируйте URL из адресной строки: это ссылка на успешный pipeline.
2. Откройте задачи **SAST — SpotBugs** и **SCA — OWASP Dependency-Check**. Сделайте снимки, на которых видны успешные шаги сканирования.
3. Внизу страницы запуска скачайте артефакты **spotbugs-sast-report** и **dependency-check-sca-report**. Откройте HTML-отчёты и сохраните снимки в **docs/screenshots/sast-report.png** и **docs/screenshots/sca-report.png**.
4. Добавьте реальные снимки в Git, затем вставьте в README следующие строки. Если отчёт показывает находку, сначала исправьте её или честно опишите результат.

   ~~~markdown
   ![SAST](docs/screenshots/sast-report.png)
   ![SCA](docs/screenshots/sca-report.png)
   ~~~
5. Сохраните README и отправьте скриншоты в репозиторий:

   ~~~bash
   git add README.md docs/screenshots/sast-report.png docs/screenshots/sca-report.png
   git commit -m "Add security scan screenshots"
   git push
   ~~~

6. После этого push дождитесь **нового** успешного запуска и сдавайте ссылку на него. Каждый push создаёт новый запуск.

В текущем локальном каталоге невозможно получить достоверные скриншоты вкладки Actions или ссылку на её успешный запуск до публикации проекта.

## Как создать публичный репозиторий и отправить проект

Локальный Git уже инициализирован, проект закоммичен в ветке `main`. На GitHub создайте **пустой публичный репозиторий** без автоматического README, .gitignore и лицензии. В терминале из папки с pom.xml выполните, заменив примерный URL своим:

~~~bash
git status
git remote add origin https://github.com/<ВАШ_ЛОГИН>/<ИМЯ_РЕПОЗИТОРИЯ>.git
~~~

Затем добавьте **NVD_API_KEY** в Settings репозитория, как описано выше. После этого отправьте код:

~~~bash
git push -u origin main
~~~

Если у репозитория уже есть origin, посмотрите его командой **git remote -v** и при необходимости измените через **git remote set-url origin <НОВЫЙ_URL>**.

GitHub может запросить вход через браузер или токен доступа. После push перейдите на страницу репозитория, проверьте файлы и вкладку **Actions**. Если секрет NVD был добавлен позже первого push, запустите workflow вручную.

## Что сдавать

1. **Ссылку на публичный репозиторий** вида https://github.com/ВАШ_ЛОГИН/ИМЯ_РЕПОЗИТОРИЯ.
2. **Текст README.md** из репозитория с описанием API, мер защиты и реальными скриншотами SAST/SCA.
3. **Ссылку на последний успешный запуск GitHub Actions** вида https://github.com/ВАШ_ЛОГИН/ИМЯ_РЕПОЗИТОРИЯ/actions/runs/НОМЕР.

Перед сдачей убедитесь, что в README нет значения JWT_SECRET_BASE64, NVD_API_KEY, действующего JWT или настоящих паролей. Примеры в этом файле используют учебный пароль только для локальной H2-базы.
